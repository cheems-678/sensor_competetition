## 一、这一版改了什么

| 项 | 旧方案（已废弃） | 现方案 |
|---|---|---|
| 显示 | `tftlcd3_5` 3.5" 彩屏，8080 **16 位**并口，占满 PB0~PB15 | `i2c_oled_128x64_096` **0.96" OLED（SSD1306）**，**软件 I2C，只占 PB6/PB7** |
| 本地内容 | 480×320 横屏热力图 + 数值 + 8 组旋转自检 | **5 行 × 21 字符信息牌**：标题 / 温湿度 / 声学 / 气体 / 虫害告警 |
| 完整信息 | 全部挤在屏上 | **ESP8266 建 TCP 服务器**，手机/PC 浏览器打开 `http://<模块IP>/` 看**左侧栏分页**看板：总览页 **10 张** KPI 卡 + **两套自带 3D 场景**（粮仓三维模型 / 声学层析立体场），其余 **11 页**按指标分栏 |
| 串口 | USART1 一肩挑 | **分工**：USART1 = 虚拟终端/上位机（协议帧）；**USART3 = ESP8266 专口** |
| 被挤走的引脚 | 超声波 TRIG、DHT11、RGB 等被迫改到 PA/PC | **PB 口整体释放**，外设回到自然位置 |
| 状态灯 | PC13/PC14/PC15 三路 GPIO 开关（只能出 8 色，「黄」= 红+绿各半） | **`AlarmLight` 报警灯**（信号线 → **PB12**，2026-10-03 由 PA3 挪来）：单色、只有亮/灭，**用闪烁节奏表达等级**（灭 / 慢闪 500ms / 快闪 150ms），PC13~15 释放为空闲 |
| 舱外光照 | 无（平台 173 器件里也没有专门的照度计） | **光敏电阻模块**（`photosensitive_resistance`）AO → **PA4 / ADC1_IN4**；**固件零协议代码** —— 平台前端自己把电压灌进 ADC（见 3.7） |
| 补光 | 只有 1 盏诱虫灯（PA11） | **普通 LED**（阴极接地，阳极串 10 K 电阻 → **PA5**），由舱外光照 **PWM 连续调光**：占空比 = 100 − 光照(%)，见 3.7 |
| 气体 | MQ-135，AO = PA5（一度因 PA5 让位而作废） | **恢复，并换了脚**：AO → **PA6 / ADC1_IN6**、DO → **PA7**；`GAS_ENABLE=1` |
| 粉尘 | GP2Y1014AU，LED = PA8、VO = PA6 | **作废**（PA6 让给 MQ-135 的 AO）：`DUST_ENABLE=0`，连 `GP2Y_LED_ON/OFF` 两个驱动宏一起 `#if` 关掉，判据摘除，三处显式 `--` |

> **2026-10-02 二次改动**：状态灯由 PC13~15 三色开关换成 PA3 上的状态灯（详见 3.6）；
> 固件里的 `DHT_PIN_DEFAULT`（**代码默认值**，与实际接线无关）由 PA3 改为 **PA1**，扫描候选表由 13 脚减到 12 脚
> —— 目的是让 PA3 彻底不被 DHT 扫描脉冲打扰。
> **2026-10-03 三次改动（现行）**：接入 **485 风速 `ZTS_3000_FSJT`（`USE_WIND485 1`）**，占 **USART2（PA2/PA3）**；
> 代价是**报警灯信号线 PA3 → PB12**、**超声波 Trig PA2 → PB1**（各挪一个空闲脚）。
> PA2/PA3、PB1、PB12 三处均已从「舱外 DHT11 扫描候选脚」表里剔除 ⇒ **候选脚 10 → 8 个**。
> **本项目实际接线：舱外 DHT11 = PA1、仓内 DHT11 = PA14、报警灯 = PB12、超声波 Trig = PB1、485 风速 A/B = PA3/PA2**，互不冲突。
>
> **2026-10-02 三次改动（两次实测修正）**：先试 `BK_SK6812` 单总线全彩灯。
> ① 按真实灯珠的 **800 kHz（0.3/0.6 µs）** 发 → 平台分辨不了这 0.3 µs 的差，**灯发纯白**（每位被误判成 1 → `0xFF×4`）。
> ② 改成放大到 **3 µs / 20 µs**（1 MHz 时基）→ **灯变成黑色灯罩、一个颜色都不下发**（平台整帧丢弃）。
> ⇒ 结论：0.3 µs 级位宽在平台上**根本分不开**，6 轮候选扫描也救不回来（推理链见 3.6 末尾的教训段）。
>
> **2026-10-02 四次改动（现行方案）**：状态灯改用 **`AlarmLight` 报警灯**（单色）——
> 单色灯只要一个电平，没有位宽问题。红引线 → 5V 电源符号，黑引线 → **PB12**（2026-10-03 由 PA3 挪来；PA3 让给 USART2 的 485 RX）。
>
> **2026-10-04 四次改动（现行）**：
> ① **报警灯 / 485 之争落定** —— 用户找到 **TTL 转 485 模块** ⇒ 报警灯留在 **PB12**、485 留在 **PA2/PA3**，
>   **零代码改动**，只改电路连线（详见 3.8 末尾）。
> ② 新增 **雨量传感器 `BK_Raindrop`（DO→PC14）**：**降雨即强制停全部风机**，见 **3.9**。
> ③ 新增 **北斗定位 `BK_BDS`（TX→PB2，软件串口）**：坐标上网页，见 **3.10**。
>   代价是 **`DHT_IN_ALT` PB2 → PA8**、**PB2 从 DHT 扫描候选表剔除**（候选脚 **8 → 7**）。
> ④ 页面从 13 项导航扩到 **15 项**（+雨量监测 / 北斗定位），整页 LZSS 后 **27828 字节**
>   （由 47464 压缩，省 41.4%），Flash 占用约 **92.5%、余量约 4.9 KB**。
> ⑤ **北斗"网页永远收不到"的排障**（同日）：接收改成"**见到起始位就一路收到底**"
>   （旧版每片只收 1 个字节，一行 73ms 永远凑不齐），并新增**线路体检** ——
>   翻转次数 / 最短脉宽→波特率 / 高占比→极性，能自动定档。见 **3.10**。
> 亮灯电平用 `ALARM_ACTIVE_LOW` 开关 + **开机 `alarm_probe()` 两轮实测**（低 2s / 高 2s）当场定案，不猜。
>
> **2026-10-02 五次改动**：加**光敏电阻模块**（AO → **PA4 / ADC1_IN4**，感知舱外光照）
> 与第 2 盏 `Plant_Light` 作光控补光灯（信号线 → **PA5**，光照低于 30 % 自动点亮）。
>
> **2026-10-02 六次改动（现行）**：
> ★ **PA5 上的灯带换成一盏普通 LED**（阴极接地，阳极串 **10 K** 电阻 → PA5），并且**由光照连续调光**，
>   不再只是「低于 30 % 就点亮」的开关式判据。
> ★★ **PA5 在 STM32F103 上没有任何定时器通道**（TIM2 在 PA15/PB3/PA2/PA3、TIM3 在 PB4/PB5/PB0/PB1、
>   TIM1 在 PA8~PA11、TIM4 在 PB6~PB9 —— 四路全查过），**做不了硬件 PWM** ⇒ 用 **TIM1 微秒时基做软件 PWM**：
>   把主循环原有的 10 ms 空等切成 10 个 1 ms 片，前 n 片亮、其余灭 ⇒ **100 Hz（人眼无闪烁）、10 档占空比**，
>   而且**不额外占用时间**（原来那 10 ms 本来就是在空等）。
> ★ 电路决定极性：**阴极接地 ⇒ 只有 PA5 输出高才有电流 ⇒ 高电平点亮**，所以**不用做极性扫描**，
>   开机只做「能亮 / 能灭」两轮自检。
> ★ **MQ-135 复活并挪脚**：AO → **PA6**（ADC1_IN6）、DO → **PA7**，`GAS_ENABLE=1`。
> ★ **代价要写清楚**：PA6 原本是粉尘模块 GP2Y1014AU 的 VO，同一个脚不能既是粉尘 ADC 又是气体 ADC，
>   所以**粉尘这一路就此作废**（`DUST_ENABLE=0`）—— 不是「读成 0」，而是**连 `GP2Y_LED_ON/OFF` 两个驱动宏
>   一起被 `#if` 关掉**、判据摘除、三处显示 `--`，PA8（粉尘 LED）释放为空闲。
> ★ 光敏模块是**「前端灌 ADC」型**元件（组件里 `send({type:"analog_type", id:"<节点>.ADCx_IN4", data:电压})`），
>   固件一行解码都不用写；但「电压高 = 亮 还是 = 暗」在服务端算、读不到 —— 串口每 2 s 打
>   `LGT=xx% raw=… mv=… duty=xx%`，拖一下元件上的滑条就能定 `LIGHT_INVERT`。

> **2026-10-03 七次改动（现行）**：新增 **火焰传感器 `BK_Flame` / `Flame_Sensor`**（**DO → PB0**）
> 检测**舱外火源**，作为**独立的一票否决级告警**（报警灯快闪 150 ms + 蜂鸣器 1 s 间歇）。
> ★ **PB0 原在 `dht_cand[]`（舱外 DHT11 候选脚）里，已同步剔除** —— 扫描会把这个脚拉高拉低，
>   既干扰 DO 读数，也可能把模块输出误当成 DHT 应答。⇒ 舱外候选脚 **11 → 10**。
> ★ **极性不猜**：和 `LIGHT_INVERT` / `GLAMP_ACTIVE_HIGH` 同一套路，做成运行时变量
>   `g_flame_alow`（默认 **1 = 低电平=有火**），串口发 **`F`**（等价 `0xC5 0xBA`）当场翻，
>   一次编译就能把两种组合试全。
> ★ **不给 `flame_ok`（重要）**：DO 是"一位"数字线，平台不下发状态 与 线上真是低电平
>   在电气上**无法区分**（不像 MQ-135 能靠 AO 的 ADC 超时判无效）。所以固件不假装能自诊断，
>   而是把**原始电平**一路报到三处（OLED / 串口 / 网页都给出 `DO=x`），让"线接没接上、
>   有没有翻转"由人当场核对 —— 宁可暴露不确定性，也不编一个"设备状态正常"。
> ★ 判据的一票否决：`fl_fire` 直接进 `lv = 2`，不与温湿度的分级混算（明火没有"轻微"这一档）。

**为什么换掉彩屏**：平台 `tftlcd3_5` 的显示画布固定为 320×480，贴到横屏面板时的旋转方向无法从文档确定
（前端 `index-e551b627.js` 中 `tftlcd3_5` 组件写死 `canvasWidth 320 / canvasHeight 480`，服务端坐标空间恒为 320 列 × 480 行），
而且必须走 **16 位数据总线**才能正确解色（8 位接法会把高字节当 B 通道 → 全屏蓝黑斜纹）。调试代价远大于收益。

**换 OLED 反而是更好的设计**：128×64 只放关键摘要，完整信息交给网页 —— 现场巡检看小屏，远程监管看网页，
"屏小信息大"的分工本身就说得通。

**4 路 PWM 风扇（2026-10-01 新增，接平台 `BK_PWM_FAN_4`）**

| 引脚 | 风扇 | 定时器通道 | 说明 |
|---|---|---|---|
| **PA15** | FAN1 | TIM2_CH1（`GPIO_PartialRemap1_TIM2`） | 1 kHz，1000 级占空比 |
| **PB3** | FAN2 | TIM2_CH2（同上） | 同上 |
| **PB4** | FAN3 | TIM3_CH1（`GPIO_PartialRemap_TIM3`） | 同上 |
| **PB5** | FAN4 | TIM3_CH2（同上） | 同上 |

> 这四个脚原本是 **JTAG 调试口**（PA15=JTDI、PB3=JTDO、PB4=NJTRST），
> 当普通 IO/PWM 用前必须先 `GPIO_PinRemapConfig(GPIO_Remap_SWJ_JTAGDisable)` 把 JTAG 关掉。
> **必须是"部分重映射"**：TIM2 若用全重映射，CH3/CH4 会被推到 PB10/PB11 —— 那正是 ESP8266 的 USART3，复用脚会打架。

> **空闲可用**：PA13、PB8、PB9、PB13~PB15、PC13、PC15（PB1 已给超声波 Trig、PB12 已给报警灯、PA2/PA3 已给 USART2 的 485、
>   **PA8 已给 `DHT_IN_ALT` 备用脚、PB2 已给北斗软串口、PC14 已给雨量 DO** —— 后三个都已从 DHT 扫描候选表剔除）。
> （PA4 已给光敏电阻的 ADC、PA5 已给补光 LED、PA6/PA7 已给 MQ-135、**PB0 已给火焰传感器 DO**，
>   这**五个脚都从 DHT11 扫描候选表里剔除了** —— 扫描会拉高拉低引脚，会搅乱 ADC、还会把灯点一下。）
> ★ 注意 **PA5 上没有任何定时器通道** —— 想给这盏 LED 上硬件 PWM 只能换脚（PB0/PB1 是 TIM3_CH3/CH4 的重映射目标，
>   但本项目已改用软件 PWM，不占脚）。

### 2.2 OLED 模块（`i2c_oled_128x64_096`）四根线

| 模块丝印 | 接平台 | 说明 |
|---|---|---|
| `VDD` | **VCC_1（3.3 V）** | 屏逻辑电源 |
| `GND` | **GND_1** | 共地 |
| `SCK` | **PB6** | I2C 时钟 |
| `SDA` | **PB7** | I2C 数据（双向） |

> 模块丝印写 `SCK` 而不是 `SCL`，这是模块厂的叫法，**功能就是 I2C 的 SCL/SDA**。
> 屏全黑时的三步：① 查 VDD/GND；② 把 `main.c` 的 `OLED_I2C_ADDR` 由 `0x78` 改成 `0x7A`（部分模块 7 位地址是 0x3D）；
> ③ 把 `OLED_I2C_DELAY_US` 从 2 调到 5 放慢时序。

### 2.3 平台上要动的两处接线

1. **拆掉 3.5 寸屏的全部连线**（D0~D15、CS/RS/WR/RD、VCC/GND）→ PB0~PB15 全部释放。
2. **ESP8266 从 PA9/PA10 改接到 PB10/PB11**；虚拟终端 / 串口监视器留在 PA9/PA10。

## 三、OLED 显示内容（本地摘要，5 行）

```
┌────────────────────────────┐
│ GRAIN TOMO        WIFI:OK  │  ← 反白标题栏，右侧为联网状态（三态实测）
│ OUT 40.0C 60.0%            │  ← 舱外（DHT11 #1，脚由开机扫描认到）
│ IN  43.0C 66.0%            │  ← 仓内（DHT11 #2，固定 PA14）
│ FAN 70/70/70/00 L62%       │  ← 4 路风扇占空比 % + **舱外光照 %**（补光 LED 的输入；PA5 占空比 = 100 − L）
│ ALM:NORMAL V:343 P:0       │  ← 告警 / 等效声速 / 害虫等级
└────────────────────────────┘
```

> `OUT 40.0C 60.0%` 是**平台 DHT11 元件默认属性值**（`Temp=40 / Humi=60`），
> 也就是"舱外读通了必然显示这两个数"。**显示别的数就说明读到的不是它** —— 一眼辨真假的验算口径。
> 仓内那一路由用户接入的第二个 DHT11 决定，把它的 `Temp` 属性改成 45/50 ℃ 即可现场演示通风分级。

| 行 | 字段 | 说明 |
|---|---|---|
| 0 | `GRAIN TOMO` / 三态联网状态 | 标题 + ESP8266 状态，见下表 |
| 1 | `OUT` 舱外温度(℃) / 湿度(%) | DHT11 #1；**没读到时显示 `OUT --.-C --.-% !`** |
| 2 | `IN` 仓内温度(℃) / 湿度(%) | DHT11 #2；**没读到时显示 `IN  --.-C --.-% !`** |
| 3 | `FAN` 四路占空比 + `L` 舱外光照 | 每台 2 位、`/` 分隔（`00` = 该台停转），由内外温湿度差分级决定；末尾 `Lxx%` = 舱外光照（**读不到显示 `L--`**，此时补光 LED 占空比归 0、不动作）。**PA5 的占空比 = 100 − L**，两个数相加恒为 100 |
| 4 | `ALM:` 报警等级 / `V:` 等效声速 / `P:` 害虫等级 | 0 正常 / 1 轻度 / 2 重度 |

> 屏幕只有 5 行，所以 `TOF`、气体浓度、16×16 热力图全部交给网页端；
> 本机只留"一眼要看"的，全部数据仍会从串口/网页完整给出。

标题栏右侧的三态（`wifi_str()`，**全部是实测，没有兜底**）：

| 显示 | 含义 |
|---|---|
| `WIFI:OK` | 模块对 AT 有应答 **且** 真的连上了某一组 SSID |
| `WIFI:AT` | 模块在说话（AT 有应答），但没进任何路由器 |
| `WIFI:--` | 模块**一个字都没回** —— 与温湿度的 `--.-` 同理，不伪装成已联网 |

### 3.1 温湿度：读不到就报错，绝不编数字

**这是本版专门改掉的一个毛病。** 早期版本在 `main()` 里给了 `g.temp_x10 = 250; g.rh_x10 = 500;`
这样的"初值"兜底，一旦 DHT11 没接好、读取全部超时，屏幕上就一直显示 **25.0℃ / 50.0%** ——
看起来像正常读数，实际上一个字节都没从传感器拿到。这种"假数据"在比赛答辩里是硬伤（数据不可信），
排查时也会把人带偏。现在：

| 机制 | 行为 |
|---|---|
| 状态位 | `g.dht_ok`（**舱外**）/ `g.dht_in_ok`（**仓内**），**只有真正握手成功过一次才置 1** |
| 初值 | `g.temp_x10 = 0; g.rh_x10 = 0; g.dht_ok = 0`（仓内同理）—— 不给任何"看起来正常"的默认值 |
| OLED | 舱外未读到显示 `OUT --.-C --.-% !`；仓内未读到显示 `IN  --.-C --.-% !` |
| 网页 | 显示 `--.- &deg;C`，并在「温湿度引脚」一行报出探测到的引脚与是否应答 |
| 串口日志 | `[GT] DHT11 OUT no response` / `[GT] DHT11 IN  lost: checksum error`；只在状态翻转时报一次 |
| 校验错诊断 | `DHT11 OUT checksum error raw=50,0,25,0,76` —— 直接打出收到的 5 字节 |
| 通风决策 | **两路只要缺一路就立刻停机**（`vent_why=0`）—— 缺一路差值就是假的，绝不拿假差值去驱动执行器 |

### 3.2 DHT11 数据脚自动扫描（2026-10-01 加）

DHT11 是单总线器件，**数据接在哪根 MCU 脚上完全由接线决定**，固件里写死一个脚号很容易和实际接线对不上
（这也是"假数据一直顶着"的根源之一）。所以开机把所有**空闲脚**各做一次完整握手，哪个脚应答就用哪个脚：

```
候选脚（**8 个**；已占用的脚一步都不碰）—— 只用于**舱外**那一路
  PA1  PA0                                ← 最可能的 PA 脚排在最前
  PB2  PB8  PB9  PB13  PB14  PB15
排除：**PA2/PA3(USART2→485)** **PB1(超声波 TRIG)** **PB12(报警灯)** PA4/PA6(ADC) PA5(补光LED) PA7(MQ-DO) **PB0(火焰DO)**
      PA9/PA10(串口) PA11(诱虫灯) PA12(蜂鸣器) PA13(保留) PB6/PB7(OLED-I2C)
      PB10/PB11(ESP8266) PA15/PB3/PB4/PB5(4 路风扇 PWM) PA14(仓内 DHT11 固定脚)
      ★ PA8 粉尘作废后本已空闲，但**没加回扫描表** —— 少扫一个脚少一分搅乱的风险
每脚做一次完整握手；首个校验和正确的脚即选中；试不中的脚恢复成上拉输入
运行中若一直没认到脚：主循环每 2 s 换一根候选脚继续找 —— 现场补接线也能自愈
扫描时会跳过 PA14(舱内那一路的专用脚，绝不抢)
```

引脚编号用 `DHT_PA(n)` / `DHT_PB(n)` 编码（低 4 位是脚号、bit4 是端口），
方向/电平/读取全部按位通用（直接写 `CRL/CRH`），换脚只改一个变量 `g_dht_pin`。

### 3.2.1 开机两屏诊断（`DHT_DIAG_MODE`）

不接串口也能一眼看清"到底卡在哪"，每屏停 3 s：

```
第 1 屏「结论屏」                  第 2 屏「明细屏」
┌────────────────────────┐      ┌────────────────────────┐
│ DHT DIAG      SYS:OK   │      │ DHT SCAN       USE PA1 │
│ OUT PA1 40.0C 60.0%    │      │ A1:0 A4:1 A0:1 B0:1    │
│ IN  PA14 43.0C 66.0%   │      │ B1:1 B2:1 B8:1 B9:1    │
│ FAN 70/70/70/00        │      │ B12:1 B13:1            │
│ SWJ:OFF (PA14=DHT2)    │      │ B14:1 B15:1            │
└────────────────────────┘      └────────────────────────┘
```

| 屏幕元素 | 含义 |
|---|---|
| `OUT PA1 40.0C 60.0%` | **舱外**：实际认到的脚 + 温湿度；`NO DATA` = 这根还没读到 |
| `IN  PA14 43.0C 66.0%` | **仓内**：固定 `DHT_IN_PIN`（默认 PA14）+ 温湿度 |
| `FAN 70/70/70/00` | 4 路风扇当前占空比 % |
| `SWJ:OFF (PA14=DHT2)` | 为 PA14 全关了 SWJ；`DHT_IN_PA14=0` 时显示 `SWJ:SWD on DHT2=PA4` |
| `A1:0` | 该**候选脚**握手结果：**0=成功** / 1=无响应 / 2=校验和错（只针对舱外那一路） |
| `SYS:OK` | 平台 `delay_us(1000)` 实测确实花了约 1000 µs（拿 TIM1 当尺子量的） |
| `SYS:STUB` | **平台把 SysTick 做成了桩**：`delay_us` 瞬间返回。这正是早期"代码全对却读不到 DHT11"的元凶 |
| `CLK:?` | 连用来量尺子的 TIM1 都没在计数 —— 微秒时基不可用 |
| `USE PA1` / `NONE` | 最终选用的脚（`NONE` = 一个都没应答） |

每根候选脚的细节（拉低前等待、低/高电平实测宽度）会从 USART1 打一份：
`[GT] dht scan PA1 -> 1 ack L=--us H=--us`。

> 接好线、确认 `SYS:OK` 且某一脚 `:0` 之后，把 `DHT_DIAG_MODE` 改成 0 提速开机。
> **验算口径**：平台 `DHT11` 元件的默认属性是 **Temp=40 / Humi=60**，读通后屏上必然是
> `T:40.0C RH:60.0%` —— 数字必须是这两个，否则说明读到的不是它。

### 3.3 微秒延时：用 TIM1 自建时基，不用平台的 delay_us（关键）

平台的 `SYSTEM/delay/delay.c` 是"配 SysTick → 忙等 COUNTFLAG"的实现。**如果仿真平台只把
SysTick 做成了"标志位读得到"的桩、并不真计数**，那么 `delay_us`/`delay_ms` 会瞬间返回 ——
现象极具迷惑性：程序一路跑通、OLED 正常刷新、串口照打日志，但 DHT11 这类微秒级单总线
传感器**永远不应答**，因为 18 ms 起始脉冲被压成了几微秒。

所以本版给单总线单独配了一个不依赖 SysTick 的时基（`main.c` 四-B 节）：

| 项 | 做法 |
|---|---|
| 时基 | **TIM1 自由运行 @1 MHz**（预分频 71 → 1 µs/拍），由定时器外设自己走 |
| API | `us_dly(n)` / `ms_dly(n)`；DHT 全程只用这两个，不用 `delay_us` |
| 自检 1 | `us_dly_init()` 读两次 TIM1 计数，不变说明平台不模拟 TIM1 → `g_us_ok=0` |
| 自检 2 | 拿 TIM1 当尺子量 `delay_us(1000)` 的实际耗时 → `g_sys_ok` |
| 兜底 | TIM1 不可用 / 计数器停住（带 40 万次守卫）→ 自动退回 `delay_us()`，**绝不挂死程序** |

> **为什么是 TIM1 而不是 TIM3**（2026-10-01 迁）：4 路风扇 PWM 征用了 TIM2 与 TIM3，
> 而"时基"要 ARR 拉满 65535 才有 65.5 ms 量程、"PWM"要 ARR 定成 999 才有 1 kHz ——
> 同一个定时器的 ARR 没法同时满足两者。定时器当**纯计数器**用不占任何引脚，
> 所以改用高级定时器 TIM1：只 `TIM_Cmd` 让它计数，一个输出通道都不配，PER 重新装。
> `US_TIM` / `US_TIM_CLK()` 两个宏就是全部耦合点，以后再挪只改这两行。

驱动其余部分（`dht_read_pin()`）的时序与平台模板 `HARDWARE/DHT11/dht11.c` 逐拍一致：
主机拉低 ≥18 ms → 释放 30 µs → 从机回 80 µs 低 + 80 µs 高 → 每 bit 50 µs 低 + 26~70 µs 高。

> **位判决用「量高电平宽度」（≥45 µs 记 1）而不是「固定 40 µs 后采样」**：
> 一帧的**最后一位**之后从机就把总线释放了（线一直是高），固定采样会把它误判成 1；
> 量宽度天然避开这个坑，而且不依赖延时精度（实测 ±15% 的高电平漂移仍能全部解对）。
> 桌面仿真已验：量宽度法在"帧尾释放"和"帧尾补低"两种从机模型下都能正确解出 `[60,0,40,0,100]`。

字体取自工程自带的 `HARDWARE/LCD/font.h` 里 `asc2_1206`（6×12 点阵，行扫描、每字节一行、低 6 位有效），
驱动里**逐点搬进 SSD1306 页格式显存**，不需要任何字库转换表。

> ⚠️ **位序必须按 `bit0 在左` 解**（`on = (bits & (1u << col))`）。
> 若写成 `0x20 >> col`（bit5 在左），屏上文字会**逐字左右镜像而字符顺序不变** ——
> 看起来"每个字都认得出来，但整屏是反的"，很容易被误判成平台翻转。
> 这个方向由字库实测确定：`F` 顶横 `0x1F = 0b011111`、`L` 顶横 `0x07 = 0b000111`，
> 只有 bit0 在左时横画才起于字符左缘。
> **判别口诀**：字符顺序也翻了（标题跑到右边）= 平台/坐标问题；只有单字反了 = 字库位序问题。

驱动策略是「**本地显存 + 整屏刷新**」：`ui_draw()` 只改 1 KB 的 `oled_buf[]`，
`oled_flush()` 再按页一次写 128 字节进 GRAM —— 一次刷新只有 8×3 条命令 + 8 次数据事务，软件 I2C 也完全不吃力。

> 实现位置：`main.c` 第八节（OLED 驱动）、第十三节（界面）、第十三-B 节（ESP8266 网页服务）。

### 3.4 超声波改成电平轮询（TIM2 让给风扇）

早期超声波用 TIM2_CH1 输入捕获（PA0）。4 路风扇要 PWM 后 TIM2 被占用，于是把测距改成
**用 `US_TIM`(TIM1) 量 ECHO 高电平宽度**的电平轮询：

| 项 | 做法 |
|---|---|
| 触发 | `HC_TRIG_H()` 拉高 10 µs 再拉低（`TRIG` = **PB1**，普通 GPIO；2026-10-03 由 PA2 挪来） |
| 等待 | 轮询 `HC_ECHO_IN()` 由 0 变 1（从机约 200~500 µs 后起高），带超时守卫 |
| 计时 | `c0 = TIM_GetCounter(US_TIM)` → 等高电平结束 → `c1 - c0` 即 µs 数 |
| 距离 | `dist_mm = t_us * 343 / 2000`（温漂基线在层析里另行自标定） |
| 超时 | 全程带超时；读不到就 `g.tof_us` 保持 −1，**不编造距离** |

对应开关 `USE_TIM_CAPTURE`（现在为 **0**）。`TIM2_CaptureInit()` 整段被 `#if` 包住，
要回退到捕获法把开关改 1 即可，但那样 4 路风扇就得另找通道。

### 3.5 SWJ 释放与仓内 DHT11（★ 上实物板前必读）

这 4 路风扇 + 仓内 DHT11 指定的 5 个脚里有 4 个原本属于**调试口**：

| 脚 | 原始归属 | 释放条件 |
|---|---|---|
| PA15 | JTDI | `GPIO_Remap_SWJ_JTAGDisable`（SWJ_CFG=010，**关 JTAG 留 SWD**） |
| PB3 | JTDO | 同上 |
| PB4 | NJTRST | 同上 |
| **PA14** | **SWCLK** | `GPIO_Remap_SWJ_Disable`（SWJ_CFG=100，**JTAG + SWD 全关**） |

`main.c` 里由 `DHT_IN_PA14` 一个开关决定：

```
DHT_IN_PA14 = 1 （当前默认）→ 全关 SWJ，仓内 DHT11 接 PA14
                             代价: 真实硬件上 ST-Link 再也连不上芯片
DHT_IN_PA14 = 0            → 只关 JTAG，SWD 保住，仓内 DHT11 改接 PA4(DHT_IN_ALT)
```

> ⚠️ **仿真平台不受影响**（虚拟 MCU 不检查 SWJ），所以演示用 `1` 没问题。
> **上实物板前请把 `DHT_IN_PA14` 改成 0**：PA14 是 SWCLK，关掉 SWD 后芯片等于把自己锁在
> 调试口外面，只能把 BOOT0 拉高进系统存储器启动、用串口 ISP 重烧才能救回来。
> 改成一个 PA4 只是一根线的事，却能彻底避免这个风险。开机第 1 屏会明确显示当前取舍
> （`SWJ:OFF (PA14=DHT2)` 或 `SWJ:SWD on DHT2=PA4`），不会让人猜。

### 3.6 报警灯 AlarmLight（信号线 **PB12**，2026-10-03 现行；由 PA3 挪来）

原先的状态灯是 **PC13 / PC14 / PC15 三路 GPIO 开关** —— 每条通道非亮即灭，只能拼出 8 种颜色。
2026-10-02 换成平台元件 **`AlarmLight`（报警灯）**：模块右侧只有**两根引线**，本设计的接法：

```
红引线 → 5V 电源符号        黑引线 → PB12（2026-10-03 由 PA3 挪来；PA3 让给 USART2 的 485 RX）
```

PC13~15 随之释放为空闲脚（★ 它们与 RTC 晶振复用，将来若要启用**不要开 LSE**）。

**灯是怎么"亮"的（读平台前端代码得到的定论）**

`AlarmLight` 前端组件的渲染逻辑只有一句 —— **只在收到 `status === "1"` 时才把"亮灯贴图"叠上去**：

```js
status === "1" ? <image href="led-*.png" width=175 height=170/> : 空
```

而 `status` 来自后端：`AlarmLight_type:"updateAlarmLight"` 下发的 `alarmLight_status[元件名]`。
也就是说 —— **亮不亮是服务端按 netlist 算出来的电流结果**，前端只负责贴图。两条推论：

1. 元件是"**负载跨在两个网络之间**"的模型：5V 那端是电源，单片机这端**拉低**才有电流通过
   ⇒ **默认低电平点亮**（`ALARM_ACTIVE_LOW = 1`）。
2. 平台**一个 status 都没下发**时，连亮灯贴图都不画，屏上只剩元件底图里那个**暗灯罩**。
   ⇒ 看着"不亮"要先分清是"平台没下发"还是"极性反了"，**别急着改接线**
   （这与 SK6812 那次的"黑罩"是同一回事，见下面教训段）。

**定案：极性不猜，开机两轮实测。** `main.c` 里的 `alarm_probe()` 开机会：

| 轮 | 驱动 | OLED / 串口 | 看到灯亮了说明 |
|---|---|---|---|
| 1/2 | 低电平 2 s | `[ALM] probe 1/2: drive LOW 2s` | `ALARM_ACTIVE_LOW` 保持 **1**（即默认值，不用改） |
| 2/2 | 高电平 2 s | `[ALM] probe 2/2: drive HIGH 2s` | 把 `ALARM_ACTIVE_LOW` 改成 **0** |

两轮都不亮 → 先查接线：信号线是否落在模块引线的外端、另一端是否接在 **5V 或 3.3V**
（模块供电 3.0 ~ 5.0 V 都行）电源符号上。延时用 `ms_dly`（平台的 `delay_ms` 是桩，会一闪而过）。

**工作时的闪烁节奏 —— 什么条件闪什么节奏**（等级 `lv` 由 `alarm_update()` 算出）

单色灯只有"亮/灭"两态，所以**用节奏表达等级**，由 `alarm_lamp_task()` 在主循环 10 ms 节拍里刷
（不阻塞、不 delay，节奏只由 `millis()` 决定，与采集周期无关）：

| 灯 | 等级 | 触发条件（**满足任意一条**即达该级） |
|---|---|---|
| **灭** | `lv = 0` 正常 | 下面两条一条都不满足 |
| **慢闪**（500 ms 亮 / 500 ms 灭） | `lv = 1` 预警 | 虫害 = 1 · ~~粉尘 > 250 µg/m³~~(**粉尘已作废**) · 声速偏差 > 10% · 气体 > 50‰ · **仓内温度 > 30.0 ℃** · **仓内湿度 > 70.0 %** · **仓内比舱外高 5.0 ℃** · **仓内比舱外潮 10.0 %RH** |
| **快闪**（150 ms 亮 / 150 ms 灭） | `lv = 2` 报警 | **火焰传感器检出火源（2026-10-03 · 一票否决）** · 虫害 ≥ 2 · MQ-135 硬件 DO 报警 · ~~粉尘 > 500 µg/m³~~ · 偏差 > 25% · **仓内温度 > 35.0 ℃** · **仓内湿度 > 80.0 %** · **仓内比舱外高 8.0 ℃** · **仓内比舱外潮 20.0 %RH** |

> ★ **温湿度相关的四条判据**：绝对阈值看**仓内**那一路；内外差看「仓内 − 舱外」，
> 且**必须两路 DHT 都有效**才算（缺一路差值就是编的，任一无效则差按 0 处理，不会凭空报警）。
> 舱外那一路仍然只作参照，单独读不到不会触发告警。
>
> ★ **"气压异常"这一路用的是替代量**：平台 173 个器件里**没有气压/风压传感器**
> （**2026-10-03 起「风压」已改为由 485 实测风速推导动压 q≈0.6·v²，见 3.8**），
> 所以这一路由 **MQ-135 气体浓度**（含硬件 DO 阈值报警）、**粉尘浓度**与**声速偏差**共同承担 ——
> **不编造一个假的气压数值**出来凑指标。
> ★ **2026-10-02 六次改动后**：气体这一路**恢复**（AO 由 PA5 挪到 **PA6**、DO → **PA7**，`GAS_ENABLE=1`），
>   粉尘这一路则**作废**（PA6 让给气体，`DUST_ENABLE=0`）。
>   答辩口径就照实说：「平台无气压传感器，用**气体浓度 + 声速偏差**作替代，不造假气压值」。
>
> **现场演示最省事的办法**：改平台里接 PA14 那颗 DHT11 元件的属性 ——
> `Temp` 由 40 改成 **46**（比外面高 6 ℃）→ 慢闪；改成 **50**（高 10 ℃）→ 快闪；
> `Humidity` 改成 **85** → 快闪。**这两个属性一改，灯和风扇会同时动**
> （风扇那套判据见 6.1），一次操作演示两个功能。

**相关宏**（`main.c` 文件头）

| 宏 | 默认 | 说明 |
|---|---|---|
| `LAMP_KIND` | 1 | **1 = 报警灯 AlarmLight（现行）；0 = 旧的 SK6812 单总线灯**（代码整段保留在 `#if LAMP_KIND == 0` 里，随时可切回） |
| `ALARM_ENABLE` | 1 | 0 则关闭报警灯，其它功能不受影响 |
| `ALARM_PIN` / `ALARM_PORT` | `GPIO_Pin_12` / `GPIOB` | 信号线 = **PB12**（2026-10-03 由 PA3 的 `GPIO_Pin_3`/`GPIOA` 挪来） |
| **`ALARM_ACTIVE_LOW`** | 1 | **1 = 拉低点亮**（5V 在另一端，有电流通路）；**2/2 轮亮就改成 0** |
| `ALARM_SLOW_MS` | 500 | 预警档闪烁周期（ms） |
| `ALARM_FAST_MS` | 150 | 报警档闪烁周期（ms） |

**曾经的 SK6812 教训（保留备查，也是"别猜平台元件"的活教材）**

换报警灯之前先试过 `BK_SK6812` 单总线全彩灯，两次烧写实测到两个完全不同的"灯不正常"：

| 用的时序 | 灯珠实际表现 | 含义 |
|---|---|---|
| 标准 800 kHz：0 码 0.30 µs / 1 码 0.60 µs | **最亮的纯白** | 32 位全被判成 1（`0xFF×4`） |
| 放大：0 码 3 µs / 1 码 20 µs（位周期 30 µs） | **一直是黑罩，什么也不发生** | 平台**整帧丢弃**，连颜色都不下发 |

后面做过 6 轮候选时序扫描（`SK_TRY[]`，含两轮"发反相色"=`要它显红就发 (0,255,255)`），
也没能从平台上稳定拿到颜色。**根因**：平台把元件的波形解析放在服务端编译出来的
**`libsim-<type>.so`** 里（前端 `moduleUtils` 逐个元件编译），判据在前端读不到；
而 0.3 µs 级的位宽**低于平台的时间分辨率**，怎么调都在"全 1"和"整帧丢弃"之间打转
（对照：DHT11 的 0/1 码差 44 µs，比 SK6812 的 0.3 µs 大 150 倍，所以 DHT 读得通）。
⇒ **改用单色报警灯**：只要一个电平，没有位宽问题；`LAMP_KIND` 一改就能切回旧代码。

### 3.7 光敏电阻（PA4）→ 光控补光 LED（PA5，软件 PWM 连续调光）（2026-10-02）

**这一组是「输入 → 判断 → 执行」最完整的一条链**：光敏电阻读舱外光照 → 算出补光占空比 → 用软件 PWM 调 LED 亮度。

> **与上一版的区别**：上一版是「光照 < 30 % 就点亮」的**开关式**判据（`LIGHT_DARK_PCT`）；
> 这一版改成**连续调光** —— `占空比 = 100 − 光照(%)`，环境越暗补得越亮，拖滑条能看到亮度连续变化。
> `LIGHT_DARK_PCT` 这个宏**已不再参与控制**（只留在注释里说明沿革）。

#### ① 光敏电阻模块：固件零协议代码

从平台前端分块（`index-e551b627.js`）里读到的组件实现：

```js
watch: {
  photosensitive_resistance_adc: function (v) {
    send({ type: "analog_type", id: `${node}.ADCx_IN${ch}`, data: v.voltage })
  }
}
```

也就是说**前端自己算出这个元件接在哪个 ADC 通道，再把电压直接灌进仿真**，
固件只要 `adc_read_avg_safe(ADC_Channel_4, 8)` 就能拿到值 —— **一行解码都不用写**。
（同机理的还有 `potentiometer` 电位器、`adc` 滑条，都是「前端灌 ADC」型。）

★ 但**「电压高 = 亮 还是 = 暗」读不出来** —— 电压是服务端算的，前端只负责转发。
所以只做线性归一化，方向交给 `LIGHT_INVERT`，**由实测定**：

| 你的操作 | 看串口 | 结论 |
|---|---|---|
| 把光敏模块面板的滑条拖到 **100 %** | `LGT=..% raw=… mv=…` | raw **变大** → `LIGHT_INVERT` 保持 **0** |
| 把滑条拖到 **0 %** | 同上 | raw 反而**变大** → `LIGHT_INVERT` 改成 **1** |

串口每 2 s 打一次（`send_ascii_log()`），**并把算出来的占空比一起打出来**：
`... LGT=62% raw=2540 mv=2048 duty=38% (auto) ...`

#### ② 有效性判据：宁可 `--`，不猜

| 情况 | 处理 |
|---|---|
| ADC 超时（返回 0） | `light_ok = 0` → 屏上 `L--`、网页 `-- %`、串口 `LGT=--`、`duty=0%` |
| 有读数，哪怕是 0 % | **有效**（真·全黑也是有效读数）→ 全黑时占空比给到 **100 %**，这正是该有的反应 |

★ 关键：**不能把「电压 = 0」当成「没接」** —— 夜里/全黑时电压本来就该接近 0，
那样会把「天黑了」误判成「传感器掉了」。反过来，**无效时占空比归 0、灯不动作**：
既不因为它「看起来暗」就开灯，也不假装天亮把它关掉。

#### ③ 为什么 PA5 只能做**软件** PWM（本轮最关键的一个查证）

需求是「用 PWM 调 LED 亮度」，但**PA5 在 STM32F103 上没有任何定时器通道** —— 四个定时器全查过：

| 定时器 | 通道引脚 | 有没有 PA5 |
|---|---|---|
| TIM2 | CH1~CH4：PA15 / PB3 / PA2 / PA3（部分重映射） | 无 |
| TIM3 | CH1~CH4：PB4 / PB5 / PB0 / PB1（部分重映射） | 无 |
| TIM1 | CH1~CH4：PA8 / PA9 / PA10 / PA11 | 无 |
| TIM4 | CH1~CH4：PB6 / PB7 / PB8 / PB9 | 无 |

⇒ **硬件 PWM 在这根脚上做不到**。两个选择：① 换脚（PB0/PB1 是 TIM3_CH3/CH4 的重映射目标，有硬件 PWM）；
② 留在 PA5 做软件 PWM。**本项目选 ②**，理由见下 —— 关键是它**并不额外花时间**：

```
主循环的一个节拍本来就有一句 delay_ms(10) 在空等（10 ms 里什么也不干）
                    ↓
把这段空等切成 GLED_PWM_SLICES(10) 个 1 ms 片，逐片调用 gled_pwm_slice(k)
                    ↓
前 n 片输出"亮"、其余输出"灭"，n = round(duty / 100 × 10)
                    ↓
⇒ PWM 频率 = 1 / 10 ms = 100 Hz（人眼无闪烁），占空比 10 档（每档 10 %）
```

而 1 ms 的片长用**已有的 TIM1 微秒时基**（`us_dly(1000)`）来等 —— 它的可靠性已经在 DHT11 上验过了
（平台的 `delay_us` 是桩，会瞬间返回；`us_dly` 带 `g_us_ok` 自检与计数停摆守卫）。

> 若哪天要更细的调光（比如 1 % 一档），把 `GLED_PWM_SLICES` 改大即可，但**片长会变短、翻转更频繁**；
> 100 Hz / 10 档对"补光灯"这个用途足够，也就没把主循环切得更碎。

#### ④ 极性：这盏 LED **不用扫描**

电路是**阴极接地、阳极串 10 K 电阻接 PA5** ⇒ 只有 PA5 输出**高电平**才有电流通路
⇒ **高电平点亮，这是电路决定的，不用像报警灯那样开机试极性**。

所以开机自检从「4 轮极性测试」简化成 **2 轮「能亮 / 能灭」**：

| 轮 | 驱动 | OLED | 说明 |
|---|---|---|---|
| 1/2 | 强制 100 % 占空比，亮 2 s | `GLAMP SELF 1/2` / `LED ON 2s` / `dark? R too big` | **若不亮**：先怀疑 **10 K 太大**（3.3 V / 10 K ≈ 0.16 mA，普通 LED 基本看不见），建议换 **330 Ω ~ 1 K** |
| 2/2 | 强制 0 %，灭 1 s | `GLAMP SELF 2/2` / `LED OFF 1s` / `lit? -> send P` | **若还亮**：说明平台那头是低电平点亮 ⇒ 串口发 **`P`** 翻极性 |

#### ⑤ 控制律

| 条件 | PA5 占空比 |
|---|---|
| 光照有效 | `duty = 100 − light_pct`（**连续**；全黑 → 100 %，全亮 → 0 %） |
| 光照**无效**（`light_ok = 0`） | `0`（**不猜**，灯不动作） |
| 手动强制（`CMD_GLAMP_ON` / `CMD_GLAMP_OFF`） | 100 % / 0 %，自动逻辑让位；`CMD_GLAMP_AUTO` 交回自动 |

占空比每 10 ms 由 `glamp_task()` 重算、由 `gled_pwm_slice()` 逐片消费；光照本身每 500 ms 更新一次。

**演示办法**：把光敏模块面板上的滑条往下拖（模拟入夜），屏上第 3 行末尾的 `L` 数字一路变小，
**PA5 的占空比 = 100 − L 一路变大、灯越来越亮** —— 屏上的数字和灯的亮度用的是同一个数，
不是两件各自表演的东西。网页上「舱外光照」与「补光 LED」两行相邻，**两个百分比相加恒为 100**，一眼可对。

#### ⑥ 排障：「灯一直亮 / 一直不亮」怎么办（2026-10-02 现场遇到）

**先分清是数据问题还是驱动问题 —— 判据只有一个：把输入拉到极端，看显示值往哪边走。**

| 把光敏滑条拉到**最亮**时，屏上 `L` 显示 | 根因 | 怎么办 |
|---|---|---|
| **很低**（如 `L05%`） | **① 光照方向反了**：平台实际是「光越强 → AO 电压越低」（光敏电阻分压的常见接法），我们却按「电压越高越亮」归一化了 ⇒ 拉到最亮反而判成天黑 | 串口发 **`I`**（或 `C5 B8`）翻方向 |
| **很高**（如 `L92%`）却还亮 | **② 极性反了**：把这盏灯当成了低电平点亮 ⇒ **与光照完全无关，从头到尾常亮** | 串口发 **`P`**（或 `C5 B9`）翻极性 |
| `L--` | 光照压根没读到（ADC 超时）→ 逻辑是「不动」，不该亮；**若此时仍亮，必然是 ②** | 先查 PA4 接线，再按 ② 处理 |
| 数字对得上，但**灯完全不亮** | **③ 10 K 限流电阻太大**，电流不足以点亮 | 换成 **330 Ω ~ 1 K** |

★ 串口每 2 秒那行日志会直接把结论打出来：

```text
LGT=92% raw=3760 mv=3028 duty=8% (auto)  ← 光照很亮，占空比只有 8%，灯却在全亮 = 极性反
```

- 占空比很低（甚至 `duty=0%`）却亮着 → **极性反** ⇒ 发 `P`；
- `LGT` 与滑条**反向**走 → **方向反** ⇒ 发 `I`；
- 日志尾部是 `(manual)` → 处于手动强制状态 ⇒ 发 `C5 B7`（`CMD_GLAMP_AUTO`）交回自动；
- 日志尾部是 `(noData)` → 光照无效，占空比被强制为 0。

**★ 为什么做成"运行时可翻"，而不是改宏重传：**

光照方向（`LIGHT_INVERT`）与灯的极性（`GLAMP_ACTIVE_HIGH`）**都在服务端算，前端读不到**，
所以只能靠实测。若它们是编译期宏，**每猜错一次就要往平台重传一遍固件重新编译** ——
一轮往返很贵，而四种组合最多要试四次。改成**运行时变量**（`g_light_invert` / `g_glamp_ahigh`，
初值仍由宏给）之后，**一次烧写就能把四种组合现场试全**，试出正确的一组再把宏改掉固化即可。

同理，这里**故意不保留 `GLAMP_SET_ON/OFF` 宏** —— 留着宏就一定会有人去用它，
一用就绕过运行时极性，排障时又得再烧一遍。驱动一律走 `glamp_drive()`。

### 3.7.1 ★★ 模拟量两点定标（光敏 / MQ-135）（2026-10-04）

**症状**：光敏滑条拉到 **100 %**，网页却只显示 **33 %**；气体读数也和滑条对不上。

**根因**（反查平台前端分块确认，不是猜的）：平台这两个元件在**前端**只发一个
`proportion`（滑条 0~100 %）：

```js
// photosensitive_resistance / MQ135 组件
send(ve(1006,{type:`${type}_protocol`, id:`${name}`, proportion:String(...)}))
```

真正的「百分比 → 电压」是**服务端模型**算的，前端读不到。实测 **MQ-135 满偏只有 1287**，
根本不是 12 位的 4095 ⇒ 固件里 `adc * 100 / 4095` 必然算错（拉满只出 33 %）。

**做法**：改成**两点线性定标**，端点**现场锁定**（不用改代码、不用重传固件）：

| 串口键 | 作用 |
|---|---|
| `q` | 把**当前**光敏 raw 锁成**暗端**（记作 0 %） |
| `r` | 把**当前**光敏 raw 锁成**亮端**（记作 100 %） |
| `s` | 把**当前**气体 raw 锁成**零端**（记作 0.0 ‰） |
| `t` | 把**当前**气体 raw 锁成**满端**（记作 100.0 ‰） |

现场步骤（约 10 秒）：滑条拖到一端 → 按一次键 → 拖到另一端 → 再按一次键。

**串口每次都会打出端点与原始码**，随时可核对：

```
LGT=100% raw=1351 lo=0 hi=1351 mv=1089 ...     ← 光敏已定标
GAS=68 graw=880 glo=0 ghi=1287 ...             ← 气体已定标
```

**★ 端点数不出来（`hi <= lo`）时判无效**：屏 / 网页 / 串口三处显示 `--`，
绝不拿 0 或某个「看着合理」的百分比糊过去（硬规矩第 1 条）。
默认值里光敏的 `hi = 1287` 是**暂借** MQ-135 的实测值，**必须标定一次**才准。

**为什么不写死一个满量程**：每个元件的服务端模型不同，写死必然只对一个；
改成按键锁定后，换元件 / 平台改模型都不用重传固件。

### 3.8 485 风速传感器 + 风压推导（2026-10-03 新增）

**为什么是 USART2**：USART1 = 虚拟终端/串口监视器，USART3 = ESP8266，**只剩 USART2（PA2/PA3）**。
代价是把它俩原来的用途各挪一个空闲脚：**超声波 Trig PA2 → PB1**、**报警灯 PA3 → PB12**（纯 GPIO，换脚零代价）。

**接线（仿真）**：平台器件库里**没有 MAX485**，仿真把 A/B 差分线**等效直连 USART** ——
`黄 A → PA3(USART2_RX)`、`蓝 B → PA2(USART2_TX)`。
**实物**要加 `MAX485/SP3485`：`A→A、B→B`，`RO→PA3`、`DI→PA2`、`DE`+`RE̅` 并到一个空闲 GPIO（如 PA8）做方向切换。

**协议**：Modbus RTU 主站，9600 8N1，查询 `01 03 00 00 00 01 84 0A`（读保持寄存器 0x0000），
应答 `01 03 02 <hi> <lo> <crc-lo> <crc-hi>`，7 字节。
`wind_poll()` 每秒一次；**地址/功能码/字节数/CRC 四样全对**才认，否则 `wind_ok = 0`。
寄存器原值就是 **风速 ×10**（量程 0~600 ⇒ 0~60.0 m/s）。

**风压 = 由风速算出的动压**（板上没有风压传感器，**不编数值**）：

    q = ½ ρ v²   ≈   0.6 · v²      (ρ = 1.2 kg/m³, v 单位 m/s, q 单位 Pa)
    整数式: q×10 = wind_x10² × 6 / 100

例：v=3.2 → 6.1 Pa；v=16.0 → 153.6 Pa；v=60.0 → 2160 Pa。

**读不到就报 `--`**：`wind_ok = 0` 时屏 / 网页 / 串口三处一律 `--`，
**绝不拿 `0 m/s` 冒充"无风"**（与温度不给 25.0 ℃ 兜底同一条规矩）。

**调试**：串口发 **`V`** 翻转"每次轮询都打印 7 字节原始回帧"；
网页「风速与风压」页给出 **风速 / 动压 / Modbus 原始寄存器值 / 485 接线 / 算式** 五行，并写明风压是推导量。

### 3.9 雨量传感器 `BK_Raindrop` + 通风联锁（2026-10-04 新增）

**接线**：`DO → PC14`（`RAIN_ENABLE 1`，上拉输入）；模块的 **AO 接在 PC13 上，但读不了**
—— **PC13 不是 ADC 脚**（F103C8 只有 PA0~PA7 / PB0 / PB1 有 ADC 通道）。
本功能只需要"下没下雨"这一位，所以 AO 不接也不用，**不要**为它去改固件。

**为什么下雨要停风机**：下雨时舱外空气是高湿的，开风机等于往仓里灌潮。
所以这是一条**硬件安全联锁**，优先级**高于手动命令**。

**控制律**：`g_rain_on` 在通风决策**算完之后**执行，把 4 路风机无条件置 0：

```c
if (g_rain_on) {
    for (i = 0; i < 4u; i++) fan_set_pct(i, 0);
    g.fan_on = 0; g.fan_pct = 0;
    g.vent_why = 5u;          /* 5 = 下雨联锁 */
}
```

★ 放在决策**之后**是关键：这样 `CMD_FAN_ON`（手动开风机）也压得住它。
★ `vent_why = 5u` 是**新增的枚举值** ⇒ 页面的 `WY` 表**必须同步加第 6 项**，
否则那一行会**静默显示 `--`**（本项目已栽过一次，`_check14.py` 第 5 节现在负责兜住）。

**极性**：「有雨」是高电平还是低电平**由服务端决定，前端读不到** ⇒ 做成运行时变量
`g_rain_alow`，串口发 **`R`** 现场翻。串口每次采集都把 **PC14 原始电平**打出来，
拿水碰一下探头看它翻不翻即可定案。（与火焰传感器同一套做法。）

**页面上能看到**：左侧栏「雨量监测」页 —— 有雨画**下雨动画**（云 + 斜雨丝 + 地面涟漪），
无雨画**晴朗动画**（太阳光晕 + 光芒 + 云），主值直接写"检测到降雨 · 已停止全部风机"。

### 3.10 北斗定位 `BK_BDS` + 软件串口（2026-10-04 新增）

**接线**：模块 **TX → PB2**（`BDS_ENABLE 1`，上拉输入）。**模块的 RX 那根不用接** ——
我们只收不发。所以"模块 RX 接到 PB1（超声波 TRIG）"这件事**不构成冲突**：
UART 输入是高阻，不会被 TRIG 的脉冲影响。

**为什么用软件串口**：C8T6(LQFP48) 只有 3 路 USART —— USART1 = 终端/协议帧、
USART3 = ESP8266、USART2 的脚**固定死 PA2/PA3**（重映射目标是 PD5/PD6，**这个封装根本没有**）。
没有第四路了，只能用 bit-bang。

**怎么收（8N1，每位中心采样；`bit = 1000000/baud`，9600 → 104µs）**：

★★ **一进 `bds_task()` 就必须"一路收到底"，收一个字节就撒手是不行的。**
一行 NMEA 在 9600 下要 **73ms**，中途只要把控制权交回主循环一次（哪怕只 200µs），
后面的字节就全丢 —— 页面表现就是**永远"未收到数据"**（旧版每片只收 1 个字节，正是这个病）。
现在的结构：

```
if (线高) { n = 0; return; }             /* 空闲: O(1) 返回, 顺手丢掉半截行 */
for (guard = 0; guard < 140; guard++) {  /* 140 = "线被拉死"的兜底 */
    if (guard) 等线被拉低;               /* 字节之间没空隙: stop 位一过就是下一字节的起始位 */
    if (!bds_recv_byte(&c)) { n = 0; return; }
    if (c == 0x00) { 连撞 24 个就静默 1s 再来; continue; }   /* 线被拉死(没接/接反/没上电) */
    if (c == '\r' || c == '\n') { 存原文 + 解析; return; }  /* 两种行尾都认 */
    收进行缓冲;
}
```

★ **字节之间必须重新对齐到起始位**：`bds_recv_byte()` 的前提是"自己正站在起始位起点"，
再走半位到中心采样。不重新等一次下降沿，第 2 个字节必然采偏。
★ **调用位置**：主循环本来就空等的 **1ms 片内部忙等循环**（补光软件 PWM 那 10 片）。
不过真正决定成败的是上面那条 —— 一旦开始收，就不再依赖调用频率了。

**线路体检 —— 把"收不到"的原因分开（同日新增）**

收不到数据时，"**线没接 / 模块没往外发**" 和 "**我们波特率或极性收错了**" 是两回事，
只报一句"未收到"分不出来。做法：每 500ms 拿 **一个 1ms 空等片**采样 PB2
（**只在 `g_bds_lines == 0` 时做** —— 一旦收到数据就不再打扰接收），量三个量：

| 量 | 含义 | 怎么读 |
|---|---|---|
| `edges` 翻转次数 | 这根线动没动 | **0 = 模块根本没往这根线上发**（线没接/没上电） |
| `lo_min`/`hi_min` 最短脉宽 | 最短的那一侧 ≈ **1 个位时长** | 104µs→9600；52→19200；8→115200 |
| 高电平占比 | 突发送完就歇 2s ⇒ 占比大的那侧就是空闲电平 | **高占比 < 50% ⇒ 空闲是低 ⇒ 线路反相** |

`bds_autocfg()` 据此**自动定**波特率（就近吸附到 4800/9600/19200/115200，**误差 <25% 才采纳**，
差太远只上报不改档）与极性 `g_bds_inv`；接收器一律走 `BDS_LEV()`（按极性解释后的有效电平），
**反相的模块不用改硬件**。人用 `B` 手动定过档之后（`g_bds_manual = 1`）体检就不再自动改。

★ 体检只从"本片内**第 3 次跳变之后**"开始记脉宽 —— 片是硬切进来的，头一个脉宽可能只有
半截（比如 2µs），记进去就把"最短脉宽"污染了，反推出来的波特率全废。
★ 「最近一行原文」进 JSON 给网页看之前，**必须洗成安全字符**（不可打印/引号/反斜杠 → `.`）：
一个半角双引号就能把 JSON 字符串截断，整页取数全废。

**解析**：兼容 `$GNRMC/$GPRMC/$BDRMC/$GNGGA/$GPGGA/$BDGGA`（在**头 10 个字符里找
`RMC`/`GGA` 子串**，不按固定前缀匹配）。
`ddmm.mmmm → 度×1e6` 用**纯整数**算（不用 `atof`，newlib 的 float 扫描已被 `-u` 掉）：
`deg = ip/100; mm6 = (ip%100)*1e6 + frac; 结果 = deg*1e6 + (mm6+30)/60`。
自检：`4002.229934 → 40037166`（= 40.037166°）。

**三档状态**：`0 = 没收到 / 1 = 收到 NMEA 但未定位 / 2 = 已定位`。
★★ **未定位时坐标即便非空也不显示**（GGA quality=0 却带坐标是常见情况）—— 与"不许编兜底值"同一条硬规矩。

**串口键**：**`B`** 轮 4800/9600/19200/115200（默认 9600；人定过档后体检不再自动改）；
**`Y`** 重新体检线路（改完接线后按，会清掉旧统计）；
**`N`** 打印**体检结果**（翻转次数 / 最短脉宽 / 极性 / 实测波特率）+ 最近一行 NMEA 原文 + 计数。

**页面上能看到**：左侧栏「北斗定位」页 —— 地图网格 + 卫星信号弧 + 定位脉冲点 +
经纬度与定位状态，用于**灾害现场定位**与**粮仓实时定位**。
另有 **5 行排障明细**（线路信号 / 最短脉宽 / 实测波特率 / 线路极性 / 最近报文）。
★ 收不到时**先看第一行**：显示 `0 次电平翻转` 就说明问题在模块那一侧（线没接/没上电），
不在固件 —— 不用再怀疑软串口。
★ **没有翻转时不报极性**（显示"未测出"）：线上没信号就无从判定，编一个"正常"正是本项目禁止的假值。

## 四、网页端：完整信息在这里

### 4.1 固件侧做了什么

开机走一遍标准 AT 建网流程（`esp_start()`）：

```
AT                      → 握手：模块到底在不在（没应答就是 WIFI:--，不编造）
AT+CWMODE=1             → 站点模式
AT+CWJAP="SSID","PASS"  → 接入路由器 —— **两组 SSID 依次尝试，命中即停**
                          （见 main.c 顶部 WIFI_SSID/WIFI_PASS 与 WIFI_SSID2/WIFI_PASS2）
AT+CIPMUX=1             → 允许多连接
AT+CIPSERVER=1,80       → 80 端口开 TCP 服务器
AT+CIFSR                → 打印本机 IP（记下来，就是浏览器要输的地址）
```

> **为什么 SSID 写死在代码里？** 平台那个 `esp8266_01s_1` 元件**没有配网入口**
> （点开只有「用户手册 / AT 指令集 / 简介」三个链接），所以没有面板可填 SSID，
> 只能写进固件。为此把 SSID 做成一张表，开机按顺序试：
>
> | 顺序 | SSID | 密码 | 用途 |
> |---|---|---|---|
> | 1 | `6103` | `61034148` | **实际要连的热点**（现场/演示用，2026-10-01 确认） |
> | 2 | `HTPL` | `1234567890` | 平台 `WIFISET` 面板默认值，仅作兜底 |
>
> 增删一组只改 `esp_ap[]` 表，组数由 `sizeof` 自动算（`ESP_AP_NUM`）。
>
> 判别方式：`esp_wait()` 会把模块回复存进缓冲区，`esp_resp_has("OK")` 且无 `FAIL` 才算连上。
> **不要看屏上是否 `WIFI:OK` 就断定网通了** —— 也要看串口那行 `[GT] esp: AT ok, joined "..."`。

之后**浏览器会发两种请求，固件分两路应答**（2026-10-02 第 9 次改动：页面从此存进 Flash）：

| 请求 | 回什么 | 谁在用 |
|---|---|---|
| `GET /` | **整页 HTML**（**LZSS 压缩常量**躺在 Flash 里，发送时边解压边按 1024 字节一片流式发出） | 浏览器首次打开 |
| `GET /d?t=...` | **一小段 JSON**（实测最长 581 字节） | 页面自己的 JS，每 1 秒一次，原地刷新 DOM |

整页那一路的响应头固定为（`Content-Length` 由生成器算好写死）：

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Connection: close
Content-Length: 38733
```

**为什么改成这样（两次改动叠起来）**：

1. **2026-10-02（省 RAM）**：C8T6 只有 20 KB SRAM。原先整页 HTML 要先在 RAM 里拼好再发，
   页面一大就只能砍内容。改成**常量**后，发送时 1024 字节一片直接**从 Flash 读出去**，
   一个字节的 RAM 都不占 —— 于是页面可以做到近四万字节那种体量（**两套 3D 场景 + 10 张 KPI 卡 +
   全量传感器表**）而 MCU 毫无压力；`ESP_TXBUF_SIZE` 反而从 5632 降到 **1024**（只剩数据端点用），
   省回 4.6 KB RAM。
2. **2026-10-04（省 Flash）**：Flash 只有 64 KB，上面那个"不占 RAM"的常量是**烧在 Flash 里**的。
   页面涨到 38733 字节（≈59%）之后再加功能就顶爆 —— 加 485 风速页时平台实测：
   `region FLASH overflowed by 5060 bytes`。于是把整页改成
   **LZSS 压缩存放、发送时在 MCU 上边解压边发**：**38733 → 22599 字节（省 16134，41.7%）**，
   净余量约 10 KB。代价是解压要 **2 KB 环形窗 + 1 KB 分片缓冲**（RAM）和几十行 C。

**整页压缩（LZSS）怎么落地**（2026-10-04 第 13 次改动）

| 环节 | 在哪 | 做什么 |
|---|---|---|
| 压缩器 | `仿真平台/_lzss.py` | 字节导向 LZSS：每 8 个 token 一个 flags 字节（**LSB 优先**，位=1 匹配），字面量 1 字节，匹配 3 字节 = `(len-2)` + dist **大端**两字节；窗口 **2048** |
| 生成 | `_gen_page_c.py` | 压缩整页 → 写进 `PAGE_GEN` 区的 `PAGE_LZ`，外加四个宏 `PAGE_LZ_WIN / _LEN / _RAW / _XOR`；`Content-Length` **仍是未压缩长度 38733** |
| 解压 | main.c 十五-B 节 `pg_decode()` | 逐字节产出 → 存进 2 KB 环形窗 → 攒满 1024 就 `CIPSEND` 一片，**分片数与原来一样（38 片）** |

> ★★ **`PAGE_LZ` 里含 `0x00` 字节**（压缩数据必然如此），所以长度**只能用 `PAGE_LZ_LEN`**；
> 用 `sizeof()-1` / `strlen` 会在第一个 NUL 处**静默截断**。`_check15.py` 会扫一遍防呆。
>
> ★★ **开机自检**：`main()` 里在 `USART1_Init` 之后立刻跑一次 `pg_selftest()` ——
> **只解压不发送**，比对解压长度与 XOR，结论直接打串口：
> `[LZ] page decompress self-test OK: 38733 bytes, xor=00ac`。
> 它**不依赖 ESP、不依赖网络**，所以模块没联网也能回答"网页发得出去吗"。
> **自检没过就不发整页**，改回一个明确的 `500 PAGE DECOMPRESS FAILED - see USART1 log`，
> 免得浏览器收到半截 HTML、把人引到"网页怎么白了"的错方向。串口按 **`Z`** 可随时重跑自检
> （`L`/`K`/`A` 已被补光灯占用，所以这里用 `Z`）。
>
> ★ **为什么不用 gzip/deflate**：deflate 压得更好（窗口 4 KB 能省 23235 字节），但动态 Huffman
> 解码器要 250~350 行 C，而**本机没有任何 C 编译器**可以验证（PATH 里的 ARM_GNU 目录已不存在、
> STM32CubeIDE 那个插件只剩 `include/` 没有 `bin/`、也没有 `make`/宿主 gcc/WSL）。几百行没测过的 C
> 直接上平台 = 拿编译往返赌运气。自研格式只要 40 行，且压缩器与解码器可以在 Python 里逐字节往返验证。

### 4.2 怎么看这一页：仿真里也能看（2026-10-01 加）

**先明确一件事：仿真平台里没有浏览器。** 平台前端既没有"网页展示"类元件，也没有真的 TCP/IP 栈
（"浏览器 / iframe / 网页"逐项搜过前端包，只有无线模块那个「HTTP 请求」配置页的三个字段，
那还是模块当客户端发请求用的）。所以 `http://<模块IP>/` 在仿真里**打不开**。
为此固件专门开了一条"仿真里看得见"的通路。

| 场合 | 怎么做 | 能看到什么 |
|---|---|---|
| **仿真平台（看数值在跳，推荐）** | 见下面的 4 步 | `uart_monitor` 接收区里每 3 秒出现一段 **JSON**，各传感器的值一眼看到在变 |
| **仿真平台（看整页版式）** | `python _page_tool.py --preview --demo -o 预览.html` | 用同一份页面模板 + 样本数据生成的离线页，双击即看（不轮询） |
| **本地看轮询链路** | `python _serve_preview.py 8765 120 demo` 后浏览器开 `http://127.0.0.1:8765/` | **与固件行为一致的整页 + `/d` 端点**，页面上数值真的在跳、3D 真的在动 |
| **真实硬件** | 手机连同一 WiFi，浏览器进 `http://<模块IP>/` | 渲染好的看板：左侧栏分页，总览 10 张 KPI + 两套 3D，其余页按指标分栏 |
| **上位机（看完整界面）** | 串口导出 hex → `python sim_bridge.py --log xxx.log` → 跑 `web_host` | 3D 仓体、声速图 / 异常图、趋势曲线、回波波形、控制面板 |

**仿真里看网页：4 步**

1. 导入固件包、编译、**点「开始运行」**（停止状态下串口不收不发）；
2. 电路里放一个 **`uart_monitor`（显示名「uart监视器」）**，`RX` 接 **PA9**，GND 共地；
   点面板上的「打开串口」，波特率选 **115200**（8/N/1）；
3. 在面板下半部的「发送设置」框里输入一个字符 **`W`**，点发送；
4. 接收列表里立刻出现一段数据 JSON（`ESP_HTML_ECHO = 1` 时的表现）：

```
[GT] send 'W' ... (开机时打印的说明)
===== JSON BEGIN (541 bytes) =====
{"u":86342000,"n":1,"ss":"lamp_6103","o":[400,600,1,"PA1"], ... }
===== JSON END =====
```

> ★ 2026-10-02 起 **`W` 回吐的是数据 JSON，不再回吐整页 HTML** —— 页面现在有两万字节，
> 倒进串口监视器没有意义，而那一小段 JSON 恰好把"各传感器现在读到什么"全都摆出来了，
> 排查时比整页更好用。**整页要看版式**，用上面的本地预览或 `_serve_preview.py`。

按 `W` 之后**固件仍会照常走 `AT+CIPSEND` 把整页发给 ESP8266**（如果模块真的在）——
所以仿真里按 `W` = "手动制造一次浏览器访问"，主机得到的是一小段 JSON 便于观察，
真实链路上远端拿到的仍是完整页面。

> **为什么用 `W`？** `W` 走 USART1（虚拟终端 / 串口命令口），**完全不碰 ESP8266 那条 USART3 链路**，
> 也不需要平台真有 TCP/IP。同一根口上原有的 `0` / `1` / `2` = 注入虫害等级，互不影响。
> 应答时 `esp_serve()` 除了照常走 `AT+CIPSEND` 发往 ESP8266，还把**数据端点的 JSON**
> 回吐一份到 USART1 —— 由 `ESP_HTML_ECHO` 控制，接真实 ESP8266 上现场时置 0 即可关掉。

> ⚠️ 仿真平台的 `esp8266_01s_1` 元件**不一定真的联网**（它的仿真模型在服务端 `.so` 里，看不到）。
> 固件因此写成「只发不等死」：每条 AT 最多等几百毫秒就继续，模块不在也绝不卡住主循环。
> 状态位**只按实测应答置位**：`g_esp_at` = 模块有没有应答、`g_wifi_ok` = 有没有真连上，
> 于是标题栏是三态 `WIFI:OK` / `WIFI:AT` / `WIFI:--`。
> （旧版有个 `ESP_ASSUME_OK = 1`，模块不回话也硬显示 `WIFI:ON` —— 那是**假状态**，
> 与"温湿度不许编数字"是同一条规矩，现已默认置 0。）

### 4.3 仿真里把**真实数据**送上网页（2026-10-02 新增，不经过 ESP8266）

⚠️ 先说清楚：4.2 那条路（`W` 回吐 / 浏览器开 `http://<模块IP>/`）**至今一次都没验证过**。
仿真里的 ESP8266 能不能联网、能不能建 TCP 服务器，仍是**未知数**（见 §9 排查）。
所以另开了一条**完全不依赖 ESP8266** 的通路 —— 这条路在本机已经跑通、字节级无损：

```
固件 u1_json_report()  ──每 3 秒──▶  USART1
   → 平台 uart_monitor 元件（接收区）
     → 平台前端 Vuex  state.newGdbg.uartStr
       → 平台注入.js（在页面控制台里跑, 每 400ms 取增量）
         → POST http://127.0.0.1:8765/raw
           → _live.py
             → GET /d  →  浏览器 http://127.0.0.1:8765/   ← 3D 大屏, 数值是板子给的真值
```

**怎么跑（4 步）**
1. `python _live.py 8765`
2. 浏览器打开 `http://127.0.0.1:8765/`
3. 平台进实验页、点**运行**；F12 → Console，把 `平台注入.js` 全文粘进去、回车
4. 大屏数字开始跳。排查看 `http://127.0.0.1:8765/status`，原始串口看 `/tail`

**为什么不让脚本自己连平台 WebSocket**
平台后端限制「同一 project 只允许一条仿真连接，新连接会把旧的停掉」
（前端源码 `cmd=1002` 分支里就写着这条提示）。所以只能**读页面上那条已有连接**留下的数据。

**两个坑（都已处理）**
- 平台把串口数据存成 `"170,85,..."`（逗号分隔的十进制字节）。注入脚本切增量**必须切在逗号上**：
  按字符位置硬切会把 `170` 切成 `1` 和 `70` —— 两个都是合法字节值，**编译不报错、运行不报错，但整条数据全错位**。
- `_live.py` 只在**括号配平且能 JSON 解析**时才认这帧，半截数据一律不认，不会拿残帧当真值显示。

**固件侧开关**：`JSON_AUTO_MS`（默认 `3000`；设 `0` 则退回"只在收到 `/d` 或按 `W` 时打一次"）。
代价几乎为零：115200 下每帧约 556 字节，带宽占用不到 2%，不挤 1 秒一帧的上行协议。

> 本节这条通路**已在笔记本上端到端自测通过**（`_test_live.py`：把 603 字节按 25 次碎块
> 推进去，`/d` 还原出 603 字节，无丢失、无错位）。但**平台页面上的注入环节尚未实测** ——
> 那一步需要人在真实平台上操作（登录、运行仿真），是唯一还没验过的一环。

### 4.4 与上位机的协议同源（答辩最硬的一条证据）

USART1 仍按 `0xAA 0x55` 协议每 1 秒上传全部数据（VMAP / AMAP / SUMMARY / LEVEL / ENV / VENT / SOUND），
这份协议与实物主板、`pc_host.py`、`web_host` **完全一致**——
仿真固件不是"演示玩具"，它和真实硬件共用同一个上位机解析器。详见第五节。

---

## 五、协议映射（可直接喂给 pc_host.py）

| 类型 | 名称 | 长度 | 内容 |
|---|---|---|---|
| `0x01` | VMAP | 256 B（2 帧 × 128） | 16×16 声速图（0~255 归一化） |
| `0x02` | AMAP | 256 B（2 帧 × 128） | 16×16 异常图（0~6） |
| `0x04` | LEVEL | 4 B | 料位 mm / 仓高 mm |
| `0x05` | SUMMARY | 7 B | 主异常类型 / 置信度×1000 / 耗时 ms |
| `0x07` | ENV | 8 B | 粉尘(借 lux 字段) / **4 路风扇各自占空比** / 诱虫灯 / **害虫等级(扩展)** |
| `0x13` | VENT | 16 B | **舱外 + 仓内**温湿度 / 气压 / 通风强度 / 通风原因 / 自动标志 / 两路有效性(bit0 舱外·bit1 仓内) |
| `0x14` | SOUND | 13 B | 害虫声特征 RMS / 峰值 / 主频 / 等级 |
| `0x16` | ACK | 2 B | 命令号 + 结果 |

**下行命令**（`0xC5` + cmd）：`0xA1` 通风开 / `0xA2` 通风关 / `0xA5` 诱虫灯开 / `0xA6` 诱虫灯关 /
`0xA7` 蜂鸣 / `0xA9` 自动 / `0xAA` 手动 / `0xD0~0xD2` 害虫等级注入 / `0xC0` 重新标定声速基线。
另：虚拟终端直接发 ASCII `'0'` / `'1'` / `'2'` 也能注入虫害等级（演示兜底）；
发 ASCII `'W'` 则触发一次"网页访问"（仿真里看网页用，见 4.2）。

## 六、算法说明（写进设计报告用）

- **等效声速**：`v = 2000 · L / t`，L = 200 mm 标定声程，t 为超声波飞行时间（µs）。
- **开机自标定**：首次有效读数为基线 `v0`，偏差 `r = v / v0 − 1`。
  `r > 0` → 声速偏快 → 空洞 / 虫害蛀道；`r < 0` → 声速偏慢 → 压实 / 受潮。
- **16×16 场重建**：单射线偏差 + 旋转高斯环境场（σ = 3.2 格）+ 温湿度 / 气体 修正
  → 声速图 VMAP + 异常图 AMAP（0 正常 / 1 空洞 / 2 受潮 / 3 发热 / 4 压实 / 5 虫害 / 6 发霉）。
- **决策**：按异常等级 + 虫害等级驱动**报警灯**分档闪烁（灭 / 慢闪 / 快闪）、蜂鸣器与诱虫灯；通风由下面的 6.1 控制律独立决定。

### 6.1 通风控制律：按「仓内 − 舱外」差值分级（2026-10-01）

**不看仓内绝对值单点开风扇，而是看"仓内比舱外差多少"** —— 外面 38 ℃、里面 40 ℃ 时该抽，
外面 22 ℃、里面 26 ℃ 时更该抽；只看绝对值就分不出这两种情况。

```
dT = 仓内温度 − 舱外温度 (×10 ℃)      dH = 仓内湿度 − 舱外湿度 (×10 %RH)

need = 需求点数 (0~4)，每满足一条 +1：
    dT ≥ 20 (仓内高 2.0 ℃)          → 有换气价值
    dT ≥ 50 (仓内高 5.0 ℃)          → 差距大，加力抽
    dH ≥ 50 (仓内潮 5.0 %)          → 排湿
    仓内绝对超标 (>28 ℃ 或 >65 %)   → 兜底（外面也热，但仓内已到警戒线）
    ~~粉尘 > 300 µg/m³ → 排尘~~      → **已用 `#if DUST_ENABLE` 包住**：粉尘作废(`=0`)时这条不进编译，
                                        need 上限仍是 4（四条温湿度判据刚好能把 4 台全开）

need → 4 个通风口从 FAN1 起依次启用，每台转速随 need 递增：40 / 55 / 70 / 85 %
```

现场演示（改平台元件的 `Temp` 属性即可，不用改代码）：

| 场景 | dT / dH | need | 风扇输出 |
|---|---|---|---|
| 舱外 40 ℃、仓内 40 ℃ | 0 / 0 | 0 | 全停 `00/00/00/00` |
| 仓内改成 45 ℃ | +5.0 / 0 | 2 | `55/55/00/00` |
| 仓内改成 50 ℃ | +10 / 0 | 3 | `70/70/70/00` |
| 仓内 50 ℃ + 湿度再高 5 % | +10 / +5 | 4 | `85/85/85/85` |
| 仓内改成 26 ℃（比外面凉） | −14 / 0 | 0 | 全停（不该开） |

> `vent_why` 会一并上报/上网页：`0` 不需要 / `1` 温差 / `2` 湿差 / `3` 仓内超标 / `4` 手动。
> **两路 DHT 只要缺一路，`need` 直接置 0** —— 缺一路差值就是假的，宁可停着也不照假数据转。

### 排查清单

| 现象 | 先查 |
|---|---|
| **OLED 全黑** | VDD/GND 是否接好；SCK→PB6、SDA→PB7 是否接对；从机地址 0x78 ↔ 0x7A；`OLED_I2C_DELAY_US` 调到 5 |
| OLED 有字但花 | 软件 I2C 太快 → 加大 `OLED_I2C_DELAY_US`；或试 `OLED_HW_I2C 1` |
| **温湿度显示 `--.-` 且带 `!`** | **传感器没被读到**（这是如实报错，不是显示坏了）。`OUT` = 舱外、`IN` = 仓内，先分清是哪一路。看开机第 1 屏：`SYS:STUB` 说明是延时问题（本版已用 TIM1 时基绕开）；明细屏 12 个候选脚全是 `:1` 说明没有任何器件拉低总线 → 查 DHT11 的 VCC(3.3V)/GND/DATA |
| 温湿度数字一直不变 | DHT11 读取超时。看串口是 `no response`（线没通）还是 `checksum error raw=...`（时序被干扰，多半是数据脚接错到别的脚上） |
| 屏上数值不动 | 主循环卡在某外设初始化。BOOT_SELFTEST 能刷白说明屏没问题，问题在传感器侧 |
| **报警灯一直不亮** | ① 看开机那 **2 轮极性测试**（OLED 标题栏右侧 `1/2 LOW` / `2/2 HIGH`）：**第 2 轮才亮** → `ALARM_ACTIVE_LOW` 改 0；**两轮都不亮** → 多半是**平台没下发颜色**（前端连亮灯贴图都不画，屏上只剩元件底图那个暗灯罩，不是"灯在发黑光"）；② 查接线：信号线是否落在模块引线的外端、另一端是否接 **5V / 3.3V** 电源符号（模块供电 3.0~5.0 V）；③ 串口会打 `[ALM] probe ...` 与 `[GT] AlarmLight SIG=PA3 active_low=1`，用它对时间点 |
| 报警灯亮着但"该灭的时候还亮" | 说明有判据被满足 —— 查 `ALARM=` 那行的等级（0 灭 / 1 慢闪 / 2 快闪）。最常踩的是**仓内 DHT 元件属性**（`Temp` 默认 40 ℃ 就 > 30 ℃ 了 → 一直预警档慢闪）。想演示"正常=灭"就把**仓内**那颗 DHT11 的 `Temp` 改到 30 以下、`Humi` 改到 70 以下 |
| 灯亮/灭的节奏对不对 | 慢闪 = 500 ms 档（`ALARM_SLOW_MS`）、快闪 = 150 ms 档（`ALARM_FAST_MS`）；两者都由 `millis()` 算，与采集周期无关。节奏不对只改这两个宏 |
| **光照一直 `--` / 补光 LED 不亮** | ① 串口看 `LGT=`：`LGT=--` = ADC 超时（查 PA4 是否真接到光敏模块的 AO、模块是否上电）；`LGT=0%` 是**真·全黑**，属有效读数，此时占空比**就该是 100 %** —— 若不亮说明是驱动/接线问题而不是数据问题；② 看开机 **2 轮自检**哪一轮不亮（见 3.7 ④）；③ 串口那行尾部的 `duty=xx%` 与屏上 `Lxx%` **相加是否恒为 100**，不等就说明占空比没被正确消费 |
| 光照方向反了（越暗数字越大） | 把 `LIGHT_INVERT` 由 0 改成 1；**现场先发 `I` 试** —— 判据是拖滑条看串口 `raw`：滑条 0 % 时 raw 更大就改 1 |
| **补光 LED 一直亮**（2026-10-02 现场遇到） | **先看屏上 `Lxx%`**：拉到最亮时 `L` 很低 = 方向反(发 `I`)；`L` 很高却还亮 = 极性反(发 `P`)。串口那行 `duty=0%` 却亮着 = 极性反。完整判读表见 3.7 ⑥ |
| **补光 LED 完全不亮**（数字都对） | **先怀疑 10 K 限流电阻太大**：3.3 V / 10 K ≈ 0.16 mA，普通 LED 基本看不见 ⇒ 换 **330 Ω ~ 1 K**。排除后再按上一条查极性 |
| 想验证是不是软件 PWM 真的在跳 | 串口发 `C5 B6`（`CMD_GLAMP_ON`）强制 100 %、`C5 B7`(`AUTO`) 交回自动；或把光敏滑条从 0 拖到 100，看串口 `duty=` 从 100 连续掉到 0 |
| **气体浓度显示 `--`** | 现在 `GAS_ENABLE=1`，所以 `--` 意味着**传感器真没读到**：查 MQ-135 的 AO 是否接在 **PA6**、DO 是否接在 **PA7**、模块 VCC/GND 是否上电；看串口 `GAS=` 后面是数值还是 `--` |
| 网页里「粉尘浓度」一行是红色 `--` | **这是刻意的**：PA6 让给 MQ-135 后 `DUST_ENABLE=0`，粉尘整路作废，如实报错不是 bug |
| 网页「气体浓度」显示红色 `--（读不到 · 查 AO→PA6）` | **这也是刻意的**：MQ-135 的 AO 没接到 PA6（或 ADC 读到 0）时如实报 `--`，而不是给出 `0.0 ‰` —— 后者会把"传感器掉了"伪装成"空气很干净"（`gas_ok` 与 `light_ok` 同一口径）。查 AO 是否接到 PA6、是否共地 |
| KPI 卡里出现 `--` 而不是数字 | 那也是刻意的：对应的那一路没读到有效值。KPI **不做兜底**，读到才显示数、读不到就 `--` 且整卡变红 |
| 看不到串口打印 | 电路里要放 **`uart_monitor`（uart监视器）** 元件，**RX 接 PA9**、GND 共地；仿真**运行中**再点面板的 **「打开串口」**（按钮会变成「关闭串口」），波特率选 **115200**。`uart_terminal`（串口终端助手）是另一个元件，看打印不用它 |
| **网页打不开 / 想"打开网页"** | 仿真里**没有浏览器**，`http://<IP>/` 打不开属正常。在 `uart_monitor` 的发送框发一个 **`W`** → 一段数据 JSON 会回吐到接收列表（见 4.2）；要看整页用 `python _page_tool.py --preview --demo -o 预览.html`，要看轮询效果用 `python _serve_preview.py 8765 120 demo`。实物则查 SSID/密码与 `AT+CIFSR` 的 IP |
| 虚拟终端没有协议帧 | USART1 是否接在 PA9/PA10；波特率 115200 |
| 网页打不开 | 先看 OLED 标题栏三态：`WIFI:--` = 模块没应答（查 PB10/PB11 与模块 TXD/RXD 是否交叉、`CH_PD` 是否拉到 3.3 V）；`WIFI:AT` = 模块在但没连上（改 `WIFI_SSID/WIFI_SSID2`）；`WIFI:OK` = 网通了，此时在元件数据面板里发一字节即可拿到 HTML。仿真平台本身没有真浏览器，想要完整界面走 `sim_bridge.py` + `web_host` |

## 八、与模板、真实硬件的关系

**模板驱动一个都没调用**（它们的默认引脚与本设计冲突），全部在 `main.c` 内重新实现：

| 模块 | 实现位置 |
|---|---|
| OLED (SSD1306, 软件 I2C) | `main.c` 第八节 |
| DHT11（**两路**） | 第九节（单总线位操作 + 延时；**舱外**脚开机扫 8 个空闲脚自动认，**仓内**固定 PA14，见 3.5） |
| HC-SR04 | 第九节（Trig=**PB1**，Echo=PA0；**电平轮询量高电平宽度**，见 3.4） |
| 4 路 PWM 风扇 | 第九节（`fan_pwm_init()` / `fan_set_pct()`：PA15/PB3=TIM2_CH1/CH2，PB4/PB5=TIM3_CH1/CH2，1 kHz） |
| ~~GP2Y1014AU~~ | **已作废**（`DUST_ENABLE=0`，PA6 让给 MQ-135 的 AO）；代码整段留在 `#if DUST_ENABLE` 里，随时可恢复 |
| MQ-135 | 第九节 `gas_read()`（AO = **PA6 / ADC1_IN6**，DO = **PA7** 低电平=超阈值；`GAS_ENABLE=1`） |
| 光敏电阻（舱外光照） | 第九节 `light_read()`（AO = PA4 / ADC1_IN4；**平台元件自己灌 ADC**，固件零协议代码，见 3.7） |
| **485 风速（ZTS_3000_FSJT）** | **第六节-B `wind_poll()`**（**USART2：A→PA3 / B→PA2**，Modbus RTU 轮询寄存器 0x0000；**风压由风速算得** q≈0.6·v²，见 3.8） |
| 执行器 | 第十节（诱虫灯 PA11、蜂鸣器 PA12、**报警灯 AlarmLight = PB12**（见 3.6）、**补光 LED = PA5 软件 PWM**（见 3.7）） |
| 层析重建 | 第十一节 |
| 协议收发 | 第七 / 十四 / 十五节 |
| ESP8266 网页 | 第十三-B 节 |
| 时间基准 | 第四节（TIM4 自由运行 10 µs/tick；不模拟 TIM4 时自动回退主循环节拍） |

唯一外部依赖：`SYSTEM/delay`（`delay_us` / `delay_ms`）与 `HARDWARE/LCD/font.h`（ASCII 6×12 字库）。
ADC 也不用模板的 `SYSTEM/adc`（它的三处 `while` 无超时会死等，已自实现带超时的 `adc_safe_init()`）。

> 字库冲突处理：`font.h` 里 `asc2_1206` / `asc2_1608` 都是**定义**而非声明，`lcd.c` 也包含它，
> 直接 include 会链接报 multiple definition。main.c 用
> `#define asc2_1206 gt_font_1206` 重命名后再 include 规避。

**与真实硬件的关系**

- **同源代码**：传感器采集、层析算法、报警决策、上下行协议与实物主板一致，仅引脚映射与外设驱动层不同。
- **同一上位机**：`pc_host.py` / `web_host` 用同一解析器读这份固件的数据，无需改动。
- **可迁移**：把 `main.c` 的 OLED 驱动段（第八节）与 ESP8266 段（第十三-B 节）原样搬到实物工程，
  把 `WIFI_SSID` / `WIFI_PASS` 换成现场路由器，就是一套能跑的真机固件。
